## 6. 作品名称及介绍

**拾光 LifeLog · 本地相册的 MiniCPM 人生回顾引擎**

用了 10 年小米手机，攒下 29294 张照片、几百个 G 的回忆。不是不想回忆，是翻不动：重复的照片、找不到的那一张、记不清是哪年的哪次旅行。删吧，怕删掉真的重要；不删吧，它就一直在那里，越来越沉。

拾光 LifeLog 把这条链路跑通，全流程四步：

1. 同步：从小米云盘把相册拉回本地（只读云端，RC4 解密，sha1 双重校验，支持增量，第二次跑同一区间 2.5 秒内完成）；
2. 识别：MiniCPM-V-4.7-1B 逐张看图，产出结构化 JSON：场景、人物、地点、活动、氛围、标签。实测 Apple M6 / 16GB 上 1.2 张/秒（4 并发），全库 29,294 张单轮约 6-7 小时，支持断点续跑；
3. 聚合：纯统计把这些描述聚成「一天的样子」和 222 段「生活片段」，算出独处占比 82%、出门高峰在下午 16-17 点、带孩子的日子集中在周末这类事实；
4. 叙事：MiniCPM-V-4.5-8B 把事实写成三种视角的中文叙事——「你的这些年」「给十年后的你」「给家人的信」——以及一份四段式的自我画像（最爱拍什么 / 性格底色 / 没拍下来的那部分 / 三条建议）。

与看图说话 demo 的区别有三点。一是全部本地：模型用 openbmb 官方 GGUF，llama.cpp + Metal 加速，照片与描述一次都不出本机。二是事实约束：模型只能引用程序算出的「事实白名单」里的数字，示例输出——「2026 年 9 月 26 日，一个小女孩坐在装饰有兔子玩偶的户外场景里，表情很平静。那是你这一年唯一一次带她出门。上一次，是 2024 年」——每个数字都可核对。三是可对话：整份记忆通过 MCP 暴露给任意 AI 助手，装上就能问「我上个月常去哪」「我一个人待着的时候都在做什么」，答案带着日期和场景证据。

一句话总结：拾光把相册从「一堆图片」变成「一份关于这个人的、可检索、可追问、有情感的人生档案」，而这件事从头到尾没有离开这台电脑。

## 7. MiniCPM 承担的角色或功能

MiniCPM 在本项目里承担三个角色，覆盖「识别 → 理解 → 写作」全链路：

1. **逐张视觉识别（MiniCPM-V-4.7-1B）**：相册每张照片输入本地 llama.cpp 推理服务，模型输出结构化 JSON——场景（家/餐厅/户外/旅途）、人物构成、地点线索、正在进行的活动、整体氛围、1-3 个分类标签。它是整个系统的感知层，没有它就没有任何后续数据。实测 Apple M6 上 1.2 张/秒（4 并发），全库 29,294 张约 6-7 小时可跑完。

2. **图内文字抽取（MiniCPM-OCR-1.0）**：截屏、订单、票据、路牌里的文字单独由 OCR 模型识别，写回同一条记录的 ocr_text 字段。这是相册里最容易忽略但最有信息量的一层（能读出时间、金额、商户、地点）。

3. **叙事与画像写作（MiniCPM-V-4.5-8B）**：把统计底稿（每年出门几天、第几次带孩子、独处占比 82%、最常在下午四点拍照）写成三种视角的中文叙事——你的这些年 / 给十年后的你 / 给家人的信——以及一份自我画像。模型被硬约束：短句、不比喻、不煽情、数字必须原样引用程序算出的「事实白名单」，不许自行换算或编造。

**为什么是 MiniCPM**：这是一份本地优先的项目，相册是最隐私的数据，任何云端识别方案都意味着交出十年生活的全部画面。MiniCPM-V-4.7-1B 的 Q8 量化只有 1.1 GB，是 16GB 内存消费级电脑上唯一能与系统共存、连续跑几小时的档位；openbmb 官方发布 llama.cpp 可用的 GGUF（1B / 4.5-8B / OCR 三档），Apple Silicon Metal 加速下实测 1.2 张/秒，这让「全库理解」从演示变成日常。

## 12. 实践过程与结论

**环境**：Apple M6 / 16GB 统一内存 / macOS 27；llama.cpp 0.8.0（Metal）；Python 3.15；模型为 openbmb 官方 GGUF（MiniCPM-V-4.7-1B Q8 1.1GB、MiniCPM-V-4.5-8B Q4 5.0GB、MiniCPM-OCR-1.0 Q8 0.8GB）。

**工具**：小米云服务 App 的 CDP 调试接口取登录态；i.mi.com gallery API + RC4 块解密下载；llama.cpp 的 OpenAI 兼容接口做多模态推理；SQLite 单文件存储；Tailwind CSS v4 做回顾页。

**数据**：小米云盘全量相册 29294 张（2011-2026），本页处理其中 2023 年后的 51 张作为展示样本，已逐张描述 29,285 张（99.97%）。

**关键步骤与结论**：

1. **模型档位是硬约束**：35B-A3B 最小 IQ3 也要 14.5GB，16GB 机器装不下；1B Q8 只有 1.1GB，是唯一能连续跑几小时的档位。8B 模型 ctx 设 8192 会触发 Metal OOM，必须降到 4096——这是实测踩出来的坑。

2. **并发吞吐**：1B 单 slot 约 3s/张，改 4 slot 后整体 1.2 张/秒（提升 4.8 倍）。llama.cpp 的 -np 参数会平分 context，需要同步把 -c 乘以并发数。

3. **JSON 解析容错**：1B 模型偶发漏掉字段间逗号（226 张里 14 张）。加了一层「补逗号重试 + 字段级兜底抽取」后 0 重跑。教训：不要指望小模型输出严格 JSON，解析器要自带修复。

4. **数字白名单**：让 4.5-8B 写叙事时，它会把「检索到的 10 条证据」当成「总共 10 张照片」。改成程序先算好「事实白名单」（每年出门几天、第几次带孩子），提示词硬性要求数字原样照抄，才解决了幻觉。

5. **思考型模型的坑**：MiniCPM-V-4.5-8B 默认开启 reasoning，答案全落在 reasoning_content，content 是空的。llama.cpp 加 --reasoning off 才正常，并在代码里加了空 content 时读 reasoning 的兜底。

6. **OCR 模型**：MiniCPM-OCR 需要 llama.cpp ≥ 0.8（0.7 不认识 minicpm_ocr_1_0 投影器），且必须带 --jinja --reasoning off，否则只会回「无可读文字」。

**失败案例与能力边界**：视频不做内容识别（只登记）；小米云端删除不同步删本地；模型对「住哪、职业、身份」这类相册里没有的信息会诚实说看不到——这是期望中的行为，通过提示词明确要求「记录里没有就说看不到，不要猜测」。

## 18. 对我们的模型或者社区有什么建议，欢迎分享

三点建议：

1. **1B 档位的多模态上下文**：MiniCPM-V-4.7-1B 在长图（截图、长票据）上偶尔丢后半段文字，希望能提供官方的「分段识别」推荐 prompt 或切片策略。

2. **GGUF 的思考模式开关**：4.5-8B 这类思考型模型，GGUF 里最好内置一个「reasoning off」的默认模板变体（现在要靠 llama.cpp 的 --reasoning off 参数，用户容易踩坑——content 为空而答案全在 reasoning_content）。

3. **希望官方提供更多「端侧全流程」的参考实现**：像相册理解这种「几万张 + 16GB 内存 + 全离线」的场景，选型、量化、并发、上下文长度都互相牵制，一份官方的最佳实践文档能帮开发者省掉大量试错。
